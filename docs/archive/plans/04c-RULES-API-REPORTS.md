# 04c — Sales & CRM: business rules, API, reports, extras (sections 6 to 9 of 04-SALES-CRM.md)

## 6. Business rules and formulas

Conventions: `D()` = `Decimal` (money.ts). `round2/round3/round6` = half-up to 2 / 3 / 6 decimals; `round0` = half-up to a whole rupee (`toDecimalPlaces(0, ROUND_HALF_UP)`, 0.5 rounds up). **Never use JS `number` for money.** **Calculation is delegated to plan 03's `TaxService.compute(db, input)` (BR-SCM-01/02: half-up per component, effective-dated rates, same worked numbers)**: `modules/sales/calc.ts` (T-SAL-07) adds only what is specific to sales (discount-amount input, freight apportionment BR-SAL-05 into `charges_share`, supplier-state and place-of-supply defaults, the sum rate) and calls `TaxService.compute` with one pseudo-line per sales line (`qty 1`, `rate = taxable_value` that already includes the freight share, `discountPct 0`), so tax per line is identical to SCM's. Codes defined by plan 03 are reused (`TAX_CODE_NOT_EFFECTIVE`, `PLACE_OF_SUPPLY_MISSING`). "Ticket" = the ticket that implements and tests the rule (section 12). Error codes are `Errors.*` helpers where one exists; **new codes** are added to `apps/api/src/core/http/errors.ts` by T-SAL-06 as `new AppError(status, CODE, message, fields?)` helpers named in camelCase (e.g. `Errors.creditHold`).

### 6.1 Totals, tax and place of supply

**BR-SAL-01 Line computation.**
Rule: for each line `gross = round2(qty × rate)`; `discount_amount = round2(gross × discount_pct / 100)`; `taxable_value = gross − discount_amount + charges_share` (charges_share from BR-SAL-05, 0 when no freight); tax by BR-SAL-03/04; `line_total = taxable_value + cgst + sgst + igst + cess`. Quantity is `numeric(18,3)`, rate `numeric(18,6)`, discount % `numeric(7,4)`; the user may type a discount *amount* instead: `discount_pct = round4(amount / gross × 100)` and the typed amount is kept as `discount_amount` (never both typed). `qty > 0`, `rate ≥ 0`, `0 ≤ discount_pct ≤ 100` (a 100 % discount is allowed only on replacement orders).
Example: qty 10, rate 1,250.00, discount 5 %: gross 12,500.00; discount 625.00; taxable 11,875.00. Fractional: qty 2.500 × rate 333.333333 = 833.3333325 → 833.33.
Errors: 422 `VALIDATION_ERROR` with `fields["lines[n].qty"]` etc. Ticket T-SAL-07.

**BR-SAL-02 Header totals and round-off.**
Rule: `subtotal = Σ gross`; `discount_total = Σ discount_amount`; `taxable_total = Σ taxable_value` (includes the freight shares); `cgst_total, sgst_total, igst_total, cess_total = Σ` of the lines; `other_charges` = the freight typed by the user (≥ 0, 2 dp, shown, already inside the line taxable values); `other_charges_tax = Σ tax on charges_share`; `exact = Σ line_total`; `grand_total = round0(exact)`; `round_off = grand_total − exact` (between −0.50 and +0.49). The "GST" column of the register = `cgst_total + sgst_total + igst_total + cess_total`. Totals are **always computed by the server**; a client value is ignored.
Example (one line 10 × 1,250.00, 5 %, GST 18 %, intra-state, freight 500): charges_share 500.00; taxable = 12,500.00 − 625.00 + 500.00 = 12,375.00; half-tax = round2(12,375.00 × 18 / 200) = 1,113.75 → CGST 1,113.75, SGST 1,113.75; line_total 14,602.50; exact 14,602.50; grand_total 14,603; round_off +0.50. If exact were 14,602.49 → grand_total 14,602, round_off −0.49.
Ticket T-SAL-07.

**BR-SAL-03 Supplier state, place of supply and the GST split.**
Rule: `supplier_state` = first 2 characters of the context unit's GSTIN (unit GSTIN, else the company GSTIN; none → 422 `PLACE_OF_SUPPLY_MISSING`). `place_of_supply` default = state of the order's ship-to address (goods: where the movement terminates, IGST Act s.10(1)(a)); else the billing address state; else the customer's `state_code`; none → 422 `PLACE_OF_SUPPLY_MISSING`. The user may change it (third-party "bill-to ship-to" deliveries use the bill-to state, IGST Act s.10(1)(b), (unverified for edge cases)). `place_of_supply = supplier_state` → intra-state: `cgst = sgst = round2(taxable × gst_rate / 200)`, `igst = 0`; else `igst = round2(taxable × gst_rate / 100)`, `cgst = sgst = 0`. `cess = round2(taxable × cess_rate / 100)` in both cases. Export outside India uses state code `96`; the state list (code → name) is the GST state-code list (01 Jammu & Kashmir … 38 Ladakh, 97 Other Territory, 96 Foreign Country) held in `apps/api/src/modules/sales/common/state-codes.ts` (T-SAL-01, must include at least 01-38, 96, 97).
Example: Talwade unit GSTIN `27ABCDE1234F1Z5` → supplier_state 27. Customer in Pune (27): CGST + SGST; customer in Ahmedabad (24): IGST. Taxable 12,375.00 @ 18 %: intra 1,113.75 + 1,113.75; inter IGST 2,227.50.
Ticket T-SAL-07.

**BR-SAL-04 Tax rate resolution (effective-dated, never hard-coded).**
Rule: `tax_code` of a line = the line's `tax_code_id` if given, else `hsn_sac.default_tax_code_id` of `items.hsn_sac` (service lines: the HSN/SAC typed on the line), else 422 `VALIDATION_ERROR` (`fields["lines[n].taxCode"]`); no rate on the date → 422 `TAX_CODE_NOT_EFFECTIVE` (plan 03 code). The rate = the `tax_code_rates` row of that code with `effective_from ≤ date` and (`effective_to` is null or `≥ date`), latest `effective_from` wins. `date` = the invoice / credit-note date for invoices and credit notes; the document date for quotations and orders (their tax is indicative). Rates are therefore replaced by data, e.g. the GST 2.0 structure effective 22 Sep 2025 (5 %, 18 %, 40 % plus legacy rates for old documents, sources in §15).
Example (illustrative codes in tests): code `GST18` rate 18 from 2025-09-22; code `GST28` rate 28 with `effective_to` 2025-09-21. A quotation dated 2025-09-10 for an item on `GST28` shows 28 %; the invoice dated 2025-10-05 re-resolves the item's *current* default tax code on that date (BR-SAL-07).
Ticket T-SAL-07.

**BR-SAL-05 Freight and other charges (apportioned, taxed at the line's own rate).**
Rule: freight `F` is spread over the lines in proportion to `taxable before charges` `t_i = gross_i − discount_i`: for every line except the one with the largest `t_i` (first one on a tie) `share_i = round2(F × t_i / Σt)`; the largest line takes `F − Σ other shares`. If `Σt = 0` the whole freight goes to line 1. The share is taxed with the line (this is the composite / mixed supply treatment: freight follows the rate of the goods it is spread over; this is a design decision (unverified against all GST rulings)).
Example: F = 500.00, line A t = 11,875.00 (18 %), line B t = 4,000.00 (5 %): Σt = 15,875.00; share_B = round2(500 × 4,000 / 15,875) = 125.98; share_A = 500 − 125.98 = 374.02. A: taxable 12,249.02 → half-tax round2(12,249.02 × 18 / 200) = 1,102.41; B: taxable 4,125.98 → half-tax round2(4,125.98 × 5 / 200) = 103.15.
Ticket T-SAL-07.

**BR-SAL-06 Due date and payment terms.**
Rule: `due_date = invoice_date + days` where days = `payment_terms.due_days` of the invoice's `payment_terms_id` (default: the order's, else the customer's), else `parties.credit_days`, else 0. Quotation validity is separate (BR-SAL-25). Due date counts from the **invoice date**, not from the POD. (Early-payment discount `early_discount_pct` is stored on terms but not applied in v1: backlog X-14.)
Example: invoice 2026-11-02, Net 30 → due 2026-12-02. Error: none (negative days rejected by the terms master). Ticket T-SAL-26.

**BR-SAL-07 Invoice re-pricing of tax at the invoice date.**
Rule: an invoice line copies `rate`, `discount_pct`, `description`, `qty` (≤ dispatch / order qty) from the order line but **recomputes tax code, rate and place of supply at the invoice date** (BR-SAL-03/04). The price is **not** re-resolved (the order price stands).
Example: order dated 2026-10-01 for 100 nos at ₹100 on a code that was 28 % when ordered and is 18 % on 2026-11-02 (test data): invoice 2026-11-02 taxable 10,000.00, IGST 1,800.00 (not 2,800.00). Ticket T-SAL-26.

**BR-SAL-08 Supply types: export, SEZ, bill of supply.**
Rule: `invoice_type = 'Export (LUT)'` or `'SEZ (LUT)'`: tax amounts are 0 (zero-rated supply under a Letter of Undertaking, IGST Act s.16), `lut_ref` is required (422 `LUT_REQUIRED`), place of supply `96` (export) or the SEZ unit's state (SEZ). `'Bill of Supply'` (composition or exempt supplies): every line must have `gst_rate = 0` (422 `BILL_OF_SUPPLY_TAX`). An export that pays IGST is a normal `'Tax Invoice'` with place `96`. Currency is INR in v1 (BR-SAL-09); foreign-currency export billing is backlog X-20.
Example: LUT export, taxable 2,00,000.00 → IGST 0.00, grand total 2,00,000. Ticket T-SAL-26.

**BR-SAL-09 Currency.** Only `INR` / rate 1 in v1. Any other currency code → 422 `CURRENCY_NOT_SUPPORTED`; the DB `CHECK (currency_code = 'INR')` backs it. Ticket T-SAL-07.

### 6.2 Pricing, discount, approval, quotation, order

**BR-SAL-20 Price resolution order (customer price → price-list slab → list default → item price).**
Input `(party, item, qty, date)`. Steps, first match wins; every step is recorded in `trace[]`:
1. **Customer price**: `customer_item_prices` of the party and item, `valid_from ≤ date ≤ valid_to (or open)`, `min_qty ≤ qty`; choose the largest `min_qty`, then the latest `valid_from`. If `price` is set → `rate = price`, source `CUSTOMER`. If only `discount_pct` is set → continue with steps 2-4 to get the base and then `rate = round6(base × (100 − d) / 100)`, source `CUSTOMER`.
2. **Price list in force**: `parties.price_list_id` if set and Active/in date; else among Active, undeleted lists valid on `date` with `customer_segment ∈ {party.customer_segment, 'All'}` and `item_category ∈ {item.category, 'All'}` pick by precedence: exact segment + exact category > exact segment + All > All + exact category > All + All; ties → latest `effective_from`; else the list with `is_default`. A list whose `min_qty > qty` is skipped. Inside the list: **PRICE rows** of the item (`item_id` match, else the `item_category` match), `min_qty ≤ qty`, in validity → largest `min_qty` wins, `rate = price` (or `item.selling_price × (100 − discount_pct)/100` when the row has only a discount), source `LIST_SLAB`. If no row: the list's `base_price` (category matches) → `LIST_BASE`; else the list's `discount_pct > 0` → `rate = round6(item.selling_price × (100 − discount_pct) / 100)`, source `LIST_DISCOUNT`.
3. **Promotions**: PROMO rows of that list, active, in validity, `min_qty ≤ qty`, item or category match: the single **best** (largest `discount_pct`) promotion is returned as `promoPct` (it becomes the line's default `discount_pct`, source tag `PROMO` in `promoName`); promotions never stack.
4. **Item price**: `items.selling_price`, source `ITEM_PRICE`. None → `rate = 0`, source `MANUAL`; submit then fails with 422 `PRICE_MISSING` for that line (unless the order `is_replacement`).
Output `{rate, listRate, source, promoPct, promoName, priceListId, trace[]}`. `list_rate` = rate before the user's discount; the line stores `price_source`, `list_rate`.
Activation overlap: two **Active** lists with the same `(customer_segment, item_category, currency)` may not have intersecting `[effective_from, effective_to]` → 409 `PRICE_LIST_OVERLAP` on `activate`.
Example: item X `selling_price` 1,000; list "Dealer" (segment Dealer, All, discount 8 %), PRICE row X min 100 price 850; customer segment Dealer: qty 10 → 920.000000 (`LIST_DISCOUNT`); qty 100 → 850.000000 (`LIST_SLAB`); a customer price 800 (min_qty 50) and qty 60 → 800.000000 (`CUSTOMER`); qty 10 with a promo 3 % → rate 920.000000, `promoPct 3`.
Ticket T-SAL-18.

**BR-SAL-21 Margin and margin floor.**
Rule: `cost_rate` = moving-average rate of the line's item in the order's warehouse (`stock_balances.avg_rate` when `on_hand > 0`), else `items.standard_cost`, else 0 (then margin is unknown = `null`, the line shows a "no cost" chip and does not trigger the floor). `net_unit = round6(rate × (100 − discount_pct) / 100)`; `margin_pct = round4((net_unit − cost_rate) / net_unit × 100)` (null when `net_unit = 0`). Floor = `price_lists.margin_floor_pct` of the list used, else `sales_config.default_margin_floor_pct`. Violation: `margin_pct < floor`.
Example: rate 1,000, discount 10 % → net 900; cost 760 → margin 15.5556 % (floor 10 → ok); cost 850 → 5.5556 % → violation. Ticket T-SAL-18.

**BR-SAL-22 Discount authority and approval routing (quotations and orders without a quotation).**
Rule: `userDiscount_i = discount_pct_i − promoPct_i` (promotion part is exempt). The submitter's authority = `sales_config.discount_authority[role]` (SUPER_ADMIN 100). **Approval is needed** when any `userDiscount_i > authority`, or any margin violation (BR-SAL-21), or (orders only) `grand_total > order_value_authority[role]` (null = unlimited; BR-SAL-26). Needed → status Submitted / Pending Approval with `approval_status = 'PENDING'` and `needs_approval_reason` listing the lines; not needed → `approval_status = 'NA'` and the document goes straight to Approved. **Approver** must: hold `approve` on the page (else 403 `FORBIDDEN`), be a different user from the creator and from the submitter (403 `SELF_APPROVAL_FORBIDDEN`), and have authority ≥ the largest `userDiscount_i` and `order_value_authority ≥ grand_total` (403 `AUTHORITY_INSUFFICIENT`); SUPER_ADMIN passes. Reject needs a reason ≥ 5 characters.
Example: MEMBER (5 %) enters 8 % → Submitted, PENDING. A LEAD (10 %) tries to approve → 403 `AUTHORITY_INSUFFICIENT`; a MANAGER (15 %) approves → Approved. Ticket T-SAL-19.

**BR-SAL-23 Quotation revision.**
Rule: `revise` is allowed from Sent, Approved, Rejected, Expired (409 `CONFLICT` from Accepted, Lost, Cancelled, Draft, Submitted). Inside one transaction: insert `sales_quotation_revisions(revision_no = current, snapshot)`, then `revision_no += 1`, status Draft, `approval_status = 'NA'`, `sent_at = null`, `valid_till = max(valid_till, today + quotation_validity_days)` (only when expired). The code does not change; the register shows `R<revision_no>`.
Example: R0 Sent → revise → R1 Draft, one snapshot row with revision_no 0. Ticket T-SAL-19.

**BR-SAL-24 Order margin.** `order_margin = Σ taxable_before_charges_i − Σ (cost_rate_i × qty_i)`; `margin_pct = order_margin / Σ taxable_before_charges × 100` (4 dp, null if the sum is 0). `cost_rate` on the line is captured at line save and refreshed at submit. Example: lines taxable 11,875.00 and cost 10 × 760 = 7,600.00 → margin 4,275.00 = 36.0000 %. Ticket T-SAL-21.

**BR-SAL-25 Quotation validity and expiry.** `valid_till ≥ quote date`, default `quote_date + quotation_validity_days`. `expire` (manual, or the nightly job) moves Sent/Approved quotations with `valid_till < today` to Expired. `create-order` from an Expired quotation → 409 `QUOTATION_EXPIRED` (revise it first); from Accepted it is allowed if `accepted_at::date ≤ valid_till`. Ticket T-SAL-19, T-SAL-33.

**BR-SAL-26 Sales-order approval authority.** `submit`: if no BR-SAL-22 trigger fires, `grand_total ≤ order_value_authority[role]` and the credit check passes → Approved immediately (the creator is the approver of record, `approval_status 'NA'`). Else Pending Approval; approver per BR-SAL-22. Example: MEMBER limit ₹2,00,000: order ₹1,50,000 clean → Approved; ₹3,00,000 → Pending Approval; MANAGER (₹50,00,000) approves. Ticket T-SAL-21.

**BR-SAL-27 Quotation → order.** Allowed from Approved, Sent, Accepted (not from Draft/Submitted/Rejected/Lost/Cancelled → 409 `CONFLICT`). Copies customer, price list, place of supply, payment terms, salesperson, opportunity and lines (qty, rate, discount, tax code, price source, list_rate, cost_rate, customer part no) into a Draft order; writes `document_links(QUOTATION → SALES_ORDER)` per line with qty; marks the quotation Accepted (`accepted_at` now). Remaining quantity of a quotation line = `qty − Σ linked order qty`; a second call creates an order for the remaining quantities; none left → 409 `QUOTATION_ALREADY_CONVERTED`. The quotation's prices and freight are copied as they are (no re-pricing). Ticket T-SAL-21.

**BR-SAL-28 Customer PO reference.** Same customer + same `po_reference` (trimmed, case-insensitive) on another non-cancelled order → 409 `DUPLICATE_PO` with `fields.poReference`; resend with `confirmDuplicate: true` to proceed (a customer may split a PO). Ticket T-SAL-21.

### 6.3 Stock, reservation, delivery, dispatch

**BR-SAL-30 Availability.** `available(item, warehouse) = max(0, stock_balances.on_hand − Σ reserved_qty of sales_reservations (status Reserved / Partially Reserved) of that item and warehouse, excluding the reservation being (re)computed)`. Example: on hand 100, reserved by others 30 → available 70; a line needing 80 reserves 70, short 10, status Partially Reserved. The reservation locks the balance row (`lockBalance`) before reading availability. Ticket T-SAL-23.

**BR-SAL-31 Batch and serial.** Item `batch_tracked` → each dispatch line needs `batch_no` (422 `BATCH_REQUIRED`); `serial_tracked` → `serial_nos` must be an array of distinct strings whose length equals `qty` (qty must be a whole number) (422 `SERIAL_MISMATCH`). Until the Inventory plan ships batch balances the stock is issued at item × warehouse level and the batch/serials are only recorded (traceability); `StockPort.issue` receives them so it can switch to batch balances later (FEFO) without changing callers. Ticket T-SAL-25.

**BR-SAL-32 Reservation lifecycle and expiry.** On order approval, if `auto_reserve`, one reservation per stockable line (`Open`, `required_qty` = line open qty, `expiry_date = (order.promise_date ?? today) + reservation_hold_days`) and an immediate `reserve`. `reserve` adds `min(short, available)`; status Reserved when short = 0, Partially Reserved when 0 < reserved < required, stays Open when nothing is available. `release(qty?)` lowers `reserved_qty` (all by default → Released). Dispatch consumes: `reserved_qty −= dispatched qty`, `required_qty −= dispatched qty`; when `required_qty` becomes 0 → Fulfilled. Order cancel / short-close releases. The nightly job (T-SAL-33) releases Reserved / Partially Reserved holds with `expiry_date < today` (reason "Expired", timeline entry) and then re-runs allocation of open shortages in order of priority (Urgent, High, Normal, Low), then earliest `promise_date`, then earliest reservation created time. `extend` sets a new `expiry_date ≥ today`. Ticket T-SAL-23, T-SAL-33.

**BR-SAL-33 Open quantity, partial delivery, backorder, short close.** `open_qty(line) = max(0, qty − cancelled_qty − delivered_qty)`. A dispatch or plan line may carry at most `maxQty = round3(qty × (1 + over_delivery_tolerance_pct/100)) − delivered_qty − cancelled_qty − (qty already on other open dispatch lines of the same order line)` → else 422 `QTY_EXCEEDS_OPEN`. A partial delivery leaves the remainder open (the **backorder** is just the open quantity; status Partially Delivered). `short-close` (reason required, `delete` permission): for the chosen lines (default all) `cancelled_qty += open_qty`, the reservation is released; if nothing is open and everything delivered is invoiced the order becomes Invoiced / Delivered accordingly (BR-SAL-37). Example: ordered 100; dispatch 60 → delivered 60, open 40; a dispatch of 50 → 422; short-close → cancelled 40, open 0. Ticket T-SAL-21, T-SAL-25.

**BR-SAL-34 Dispatch posting (stock issue and COGS), reversal.** The `dispatch` action (Packed → Dispatched), one transaction, `Idempotency-Key` honoured, lock order BR-SAL-91: (1) lock the dispatch row, status must be Packed; (2) checks BR-SAL-35, BR-SAL-41, BR-SAL-51; (3) for lines in `line_no` order call `StockPort.issue` → `postMovement(voucherType 'DELIVERY', qtyOut = qty, voucherId = dispatch.id, voucherNo = dispatch.code)`; the line stores `unit_cost = issue value / qty` (6 dp), `cost_value = issue value`, `ledger_entry_id`; (4) order line `delivered_qty += qty`; consume the reservation (BR-SAL-32); (5) status Dispatched, `dispatched_at`; (6) `AccountingService.post({event 'DELIVERY_POSTED', docType 'SALES_DISPATCH', docId, date = dispatch date, payload})` with the implied journal **Dr COGS / Cr Inventory** per line at `cost_value`; (7) timeline, audit `SALES_DOC_POSTED`, update order status (BR-SAL-37), plan status, notify. Not enough stock → 409 `INSUFFICIENT_STOCK` and everything rolls back. **Cancel** after Dispatched needs `delete`, is refused with 409 `DISPATCH_INVOICED` when any line has `invoiced_qty > 0` or `returned_qty > 0`; otherwise `reverseVoucher` (existing helper) writes REVERSAL entries at the original value, `delivered_qty −= qty`, event `DELIVERY_REVERSED`.
Example: dispatch 10 nos of an item with average 120.000000 → ledger OUT 10, value 1,200.00; event lines `COGS Dr 1,200.00`, `INVENTORY Cr 1,200.00`; order line delivered 10. Ticket T-SAL-25.

**BR-SAL-35 Invoice required before a Sale dispatch.** For `dispatch_type 'Sale'` and `require_invoice_before_dispatch = true`, for every dispatch line: `order_line.invoiced_qty ≥ order_line.delivered_qty + line.qty` where the invoices counted are Posted (status Posted, Partially Paid, Paid). Otherwise 409 `INVOICE_REQUIRED` listing the lines. (GST: the tax invoice must be issued at or before removal of goods; the e-way bill needs the invoice.) Other types: no invoice, a delivery challan (BR-SAL-42). Ticket T-SAL-25.

**BR-SAL-36 Invoice policy and invoice creation.** `ON_DELIVERY` (default): `create-invoice` is made from a dispatch that is Packed, Dispatched or Delivered; each invoice line = one dispatch line with `qty = dispatch_line.qty − dispatch_line.invoiced_qty` (> 0, else skipped; none left → 409 `NOTHING_TO_INVOICE`). `ON_ORDER`: `create-invoice` from an Approved / Partially Delivered order with `qty = line.qty − cancelled_qty − invoiced_qty` (editable downwards, never above → 422 `QTY_EXCEEDS_UNINVOICED`). Posting increments `order_line.invoiced_qty` and `dispatch_line.invoiced_qty`; cancelling a Posted invoice decrements them. Over-invoicing beyond `order qty × 1.20` is blocked by the DB check. Advances for goods are received as customer advances (BR-SAL-40), not as invoices (no GST invoice for an advance in v1; time-of-supply treatment of advances for goods is a Finance/Tax topic). Ticket T-SAL-26.

**BR-SAL-37 Order status derivation.** After every change of the line counters, for orders whose status is one of Approved, Partially Delivered, Delivered, Invoiced: let `net_i = qty_i − cancelled_i`. If every line has `net_i = 0` → Closed. Else if every line has `delivered_i ≥ net_i`: Invoiced if every `invoiced_i ≥ net_i` else Delivered. Else if `Σ delivered_i > 0` → Partially Delivered. Else Approved. Draft, Pending Approval, On Hold and Cancelled are never changed by this function; Closed is final (the `close` action is allowed in Delivered and Invoiced only). Ticket T-SAL-21.

**BR-SAL-38 Re-promise history.** `repromise` on a plan appends `{from, to, reason, by, at}` to `repromise_history` and sets the new `promise_date`; the order's `promise_date` is untouched, and OTIF is measured against the order promise (BR-SAL-89). Reason ≥ 5 characters. Ticket T-SAL-24.

**BR-SAL-39 Load planning.** Utilisation = `Σ gross_weight_kg` of the dispatches with the same vehicle and `plan.planned_date` / dispatch date ÷ `vehicle_capacity_kg`; > 100 % shows a red warning (no block). Item weights do not exist in the item master yet (open question Q-07), so weights are typed on the dispatch. Ticket T-SAL-31.

### 6.4 Receipts, e-invoice, e-way, returns, credit notes

**BR-SAL-40 Receipt posting, allocation, advances, cash limit.** `post` requires `receipt_amount + tds_deducted > 0`, `payment_mode`, a context FY that is OPEN, `receipt_date ≤ today`; **cash** receipts must be `< ₹2,00,000` (Income-tax Act s.269ST) → 422 `CASH_LIMIT_EXCEEDED`. Allocation base `S = receipt_amount + tds_deducted`. **Auto allocation (oldest first):** open invoices of the customer (status Posted or Partially Paid, balance > 0, all units) ordered with the `primary_invoice_id` first, then `due_date`, `doc_date`, `code` ascending; `a_i = min(balance_i, remaining)`. Split per allocation `tds_i = round2(a_i × tds_deducted / S)` (last allocation takes the remainder so Σ tds_i = tds_deducted when fully allocated), `amount_i = a_i − tds_i`. **Manual allocation:** the client sends `allocations:[{invoiceId, amount, tdsAmount?}]`; each `amount + tdsAmount ≤ balance` (else 422 `ALLOCATION_EXCEEDS_BALANCE`); the sum ≤ S. The part not allocated is the **advance** (`unallocated`). Invoices are locked in ascending id order; `paid_amount += a_i`; status Paid when balance = 0, else Partially Paid. `cancel` / `bounce` reverse every allocation (`reversed_at`), restore balances and statuses. Event `RECEIPT_RECEIVED` payload lines: Dr `BANK_OR_CASH` (receipt_amount, account = deposit_account text), Dr `TDS_RECEIVABLE` (tds_deducted), Cr `AR` (allocated), Cr `CUSTOMER_ADVANCE` (unallocated).
Example: invoices A ₹50,000 (due 10 Oct) and B ₹30,000 (due 20 Oct); receipt ₹60,000 → A Paid; B receives 10,000 → Partially Paid, balance 20,000, unallocated 0. Receipt ₹90,000 → A and B Paid, advance 10,000.
Ticket T-SAL-28.

**BR-SAL-41 E-way bill.** Applies to a Sale / Replacement / Job Work dispatch whose consignment value exceeds `eway_threshold` (₹50,000): consignment value = `Σ grand_total` of the Posted invoices linked to the dispatch (for non-Sale types `goods_value` plus estimated tax). Then `dispatch` needs `eway_bill_no` (12 digits) → else 409 `EWAY_REQUIRED`; and a `vehicle_no` or `transporter_gstin` (Part B can be completed by the transporter) → else 422 `VEHICLE_REQUIRED`. Validity: `days = max(1, ceil(distance_km / 200))`, `eway_valid_upto = start + days × 24 h` where start = the dispatch time (validity counts from the Part B entry); if `eway_valid_upto < now` at dispatch → 409 `EWAY_EXPIRED`. The state-specific intra-state thresholds (some states differ) are out of scope; a lower per-state limit can be entered by changing `eway_threshold` (open question Q-03). Over-dimensional cargo (20 km per day) is out of scope. Example: invoice ₹72,000, distance 450 km → e-way required; days = ceil(450/200) = 3; dispatch 2 Nov 14:00 → valid until 5 Nov 14:00. Ticket T-SAL-25 (rule), T-SAL-27 (record).

**BR-SAL-42 Dispatch types and challans.** `Sale` needs an invoice (BR-SAL-35). `Sample`, `Replacement` (free of charge) and `Job Work` (goods sent for processing) move goods **under a delivery challan** (CGST Rule 55: challan in triplicate for supplies not accompanied by an invoice; job-work and returns show taxable value, tax not mandatory (the challan's serial number is consecutive; ours reuses the dispatch number)). Stock issues as `DELIVERY` and posts `DELIVERY_POSTED` with `payload.dispatchType`; Finance decides the accounts. No invoice is created for them (`create-invoice` → 409 `CONFLICT`). Job-work return tracking is backlog X-17. Ticket T-SAL-25.

**BR-SAL-43 Invoice numbering at post, posting steps, immutability.** `create-invoice` makes a Draft with `code = 'DRAFT/' + 8 hex`. `post` (one transaction, idempotent): lock invoice → status Draft; lines ≥ 1; customer Active and not Blocked (BR-SAL-61); `invoice_date` inside the context FY (OPEN), `≤ today`, and **≥ the latest posted invoice date of the same unit and FY** (else 409 `INVOICE_DATE_BEFORE_PREVIOUS`, keeps numbers and dates in order); recompute totals at the invoice date (BR-SAL-07); B2B (customer REGISTERED / SEZ / COMPOSITION) needs a valid GSTIN (422 `GSTIN_REQUIRED`); then `number = NumberingService.next(tx, {docType 'sales-invoices', unitId, fyId})` and the final code is **`<UNIT>/<FYYY>/<NNNNN>`** — unit code, FY as `yyyy` of start and end two digits (`26-27` → `2627`), a 5-digit counter: `TAL/2627/00001` (14 characters). GST Rule 46 allows at most 16 characters (letters, digits, `/`, `-`) and the IRP rejects numbers starting with `0`, `/` or `-`; a code longer than 16 characters → 500 is wrong, use 422 `DOC_NO_TOO_LONG`. `FOUNDATION-CHANGE:` statutory documents (tax invoice, credit note) use this compact format instead of `<PFX>/<UNIT>/<FY>/<0001>` (the 20-character form would fail Rule 46 and the IRP). Then: set `posted_at/by`, status Posted, counters (BR-SAL-36), `parties.last_order_date`, `irn_status` per BR-SAL-44, event `SALES_INVOICE_POSTED` with symbolic lines **Dr `AR` grand_total; Cr `SALES` taxable_total; Cr `OUTPUT_CGST` / `OUTPUT_SGST` / `OUTPUT_IGST` / `OUTPUT_CESS` the totals; and `ROUND_OFF`: Cr round_off when positive, Dr |round_off| when negative** (they balance: grand_total = exact + round_off), document links, timeline, audit. Posted invoices are **never edited or deleted**: the DB trigger refuses; the API answers 409 `RECORD_LOCKED`; corrections are credit notes (BR-SAL-46). A Draft that is deleted leaves no gap because the number is taken only at post.
Example: totals of BR-SAL-02: AR Dr 14,603.00; SALES Cr 12,375.00; OUTPUT_CGST Cr 1,113.75; OUTPUT_SGST Cr 1,113.75; ROUND_OFF Cr 0.50 → Dr 14,603.00 = Cr 14,603.00. Ticket T-SAL-26.

**BR-SAL-44 E-invoice applicability, IRN, 30-day window, cancellation.** Applicable when `(sales_config.aato > einvoice_aato_threshold (₹5 Cr) OR einvoice_force)` and `invoice_type ∈ {Tax Invoice, Export (LUT), SEZ (LUT)}` and (customer GST registration type is REGISTERED or SEZ, or the invoice is an export). B2C and Bill of Supply are not applicable. Credit notes against an e-invoiced invoice are applicable too. At post `irn_status` = `Pending` (applicable) or `Not Applicable`. **30-day limit:** when `aato ≥ einvoice_report_limit_aato` (₹10 Cr) an invoice or credit note older than 30 days (today − document date > 30) can no longer be reported to the IRP: `generate-irn` → 409 `IRN_WINDOW_EXPIRED`; the workspace and the nightly job show a warning from day `einvoice_warn_day` (25). The IRN call goes through the interface `EInvoiceGateway { generate(invoicePayload): {irn, ackNo, ackDate, signedQr}; cancel(irn, reason): void }` (T-SAL-27) with a `MockEInvoiceGateway` (deterministic test IRN: lower-case hex SHA-256 of `supplierGstin + FY + docType + docNo`, FY like `2026-27`, docType `INV` / `CRN`; the exact order of the IRN hash input follows the NIC schema (unverified here)) and a `NotConfiguredGateway` that answers 503 `EINVOICE_NOT_CONFIGURED`; the real IRP adapter is built by the Finance/Tax plan; `record-irn` stores values obtained manually. **Cancel IRN** only within 24 hours of `ack_date` (409 `IRN_CANCEL_WINDOW`); after that, issue a credit note. Cancelling an invoice that has an IRN is possible only after the IRN was cancelled. Ticket T-SAL-27.

**BR-SAL-45 Sales returns.** A return line refers to a Posted / Partially Paid / Paid invoice line of the same customer. `qty ≤ invoice_line.qty − invoice_line.credit_noted_qty − Σ qty of other live returns` (statuses Requested, Approved, Received, not yet credit-noted) of the same invoice line → else 422 `RETURN_QTY_EXCEEDS_INVOICED`. `approve` needs `approve` and ≠ creator. `receive`: per line `qty_received ≤ qty`, `qty_accepted ≤ qty_received`; for dispositions Restock, Rework, Replace, Quarantine → `StockPort.receiveReturn` (`postMovement` `voucherType 'SALES_RETURN'`, `qtyIn = qty_accepted`, `rate = dispatch_line.unit_cost` (the **original cost**, 6 dp), into `return_warehouse_id` else `sales_config.returns_warehouse_id` else the original dispatch warehouse); Scrap → no stock entry. Order line `returned_qty += qty_accepted`; dispatch line `returned_qty += qty_accepted`. Event `SALES_RETURN_POSTED` (Dr `INVENTORY` / Cr `COGS` for stock-in at `round2(qty_accepted × unit_cost)`; Dr `SCRAP_LOSS` / Cr `COGS` for Scrap). Credit is issued only for `qty_accepted`.
Example: invoice qty 10; one return of 3 live; a new return of 8 → 422 (3 + 8 > 10); 7 is allowed. Ticket T-SAL-29.

**BR-SAL-46 Credit notes and the Section 34 deadline.** A credit note is created from an invoice (`create-credit-note`, body `{reasonCode, lines:[{invoiceLineId, qty}] | amount lines}`) or from a received return. **Quantity credit notes** (reason Sales Return): `qty ≤ invoice_line.qty − credit_noted_qty`; `taxable = round2(invoice_line.taxable_value × qty / invoice_line.qty)` (the last remaining quantity takes `invoice_line.taxable_value − Σ prior credited taxable` so there is no rounding drift); **amount credit notes** (Rate Difference, Discount, Quality, Other): the line has `qty = 1`, `rate = amount` (taxable), total of such lines per invoice line ≤ `invoice_line.taxable_value − already credited`. Tax is computed at the **original invoice's** `gst_rate`, supplier state and place of supply (not today's rate) with BR-SAL-03 splitting; rounding as BR-SAL-02. **Section 34(2) CGST Act deadline** = 30 November following the end of the financial year of the invoice (invoice FY 2025-26 → 30 Nov 2026), or the date of the annual return if earlier: `gst_deadline = date(year of FY end, 11, 30)` (config month `credit_note_gst_deadline_month`). If the credit note date is after the deadline, `gst_adjusted = false`: the note is a **commercial** credit note, its tax fields are 0 and `grand_total = taxable credited` (GST cannot be reduced; Finance may cancel and agree something else with the customer; open question Q-05), shown with a warning. Posting: number `CN/<UNIT>/<FYYY>/<NNNN>` (≤ 16 characters, e.g. `CN/TAL/2627/0001`); `applied_to_invoice = min(grand_total, invoice.balance)` → `invoice.credit_note_amount += applied`, status recomputed (Paid when balance 0); the remainder is customer credit (shown in the ledger and subtracted in the credit exposure BR-SAL-50); `invoice_line.credit_noted_qty += qty`; event `CREDIT_NOTE_POSTED` (Dr `SALES_RETURNS` taxable; Dr `OUTPUT_CGST` / `OUTPUT_SGST` / `OUTPUT_IGST` tax; Cr `AR` grand_total; `ROUND_OFF` as BR-SAL-43 mirrored); e-invoice for the note per BR-SAL-44. A posted credit note is immutable (cancel only before IRN or within 24 h of IRN cancellation).
Example: invoice 10 nos taxable 12,375.00 (18 %, intra), return 4 accepted: taxable = round2(12,375.00 × 4 / 10) = 4,950.00; half-tax 445.50 each; grand 5,841.00. Remaining 6 nos credited later: taxable 12,375.00 − 4,950.00 = 7,425.00. Deadline for an invoice dated 2026-11-02 (FY 2026-27): 30 Nov 2027. Ticket T-SAL-29.

**BR-SAL-47 TDS receivable and no TCS.** There is **no TCS on sale of goods** (Income-tax Act s.206C(1H) stopped applying from 1 April 2025; the system has no TCS field and never adds one). When a customer deducts TDS on its payment (e.g. s.194C contractors, s.194Q buyers' TDS on purchases of goods above ₹50 lakh a year (unverified rate/limits per section; verify with Finance)), the receipt records `tds_deducted`; the invoice shows `tds_receivable = round2(taxable_total × rate / 100)` (information, on the taxable value excluding GST when GST is shown separately) where `rate = parties.tds_receivable_rate ?? sales_config.tds_receivable_default_rate` when `parties.deducts_tds`. A receipt's TDS for one invoice may not exceed that invoice's balance (422 `TDS_EXCEEDS_BALANCE`). Event line Dr `TDS_RECEIVABLE`. Example: taxable 1,00,000.00 at 0.1 % → ₹100.00; at 2 % → ₹2,000.00. Ticket T-SAL-28.

**BR-SAL-48 Collection actions (reminders, calls, promises, escalation).** `POST /sales/collections/actions` creates a `sales_collection_actions` row. A PROMISE needs an invoice with balance > 0 and `promise_date ≥ today`; a new promise for the same invoice sets the older OPEN promise to CANCELLED (note "re-promised"). The nightly job sets OPEN promises with `promise_date < today` and balance > 0 to BROKEN, and to KEPT when the invoice balance is 0. Escalation ladder (days past due from `dunning_days` = [1, 7, 15, 30]): rung 1 reminder, rung 2 call, rung 3 manager escalation, rung 4 "credit review" flag (the actual hold comes from BR-SAL-50 overdue rule). The Worklist is every Posted/Partially Paid invoice with `days_past_due > 0`, ordered by `days_past_due × balance` descending. Ticket T-SAL-28.

### 6.5 Credit

**BR-SAL-50 Exposure and credit check.** Credit is per customer across all units. `AR = Σ balance` of the customer's Posted / Partially Paid invoices; `unapplied = Σ unallocated` of Posted receipts `+ Σ (grand_total − applied_to_invoice)` of Posted credit notes; `open_orders = Σ over lines of orders with status Approved or Partially Delivered of (qty − cancelled_qty − invoiced_qty) × line_total / qty` (value incl. GST of what is not yet in AR; On Hold and Pending Approval orders excluded, the order being checked is excluded and added as `orderValue`). `exposure = AR + open_orders − unapplied`; **Used Limit** (page) = `max(0, exposure)`; `Available = limit − Used`. **Check** for an order: `required = exposure + orderValue`; pass when `limit IS NULL` (no limit) or `required ≤ limit + activeOverrideAmount`. `limit = 0` means no credit: passes only when advances cover the order (`required ≤ 0`). Additional fails: `overdue_amount > 0` and `oldest_due_days > max_overdue_days` (profile value else config 30) → reason `OVERDUE`; customer Blocked → `BLOCKED_CUSTOMER`. Result `{passed, reasons[], limit, exposure, orderValue, required, available, overdueAmount, oldestDueDays}`.
Example: limit 10,00,000; AR 4,00,000; advances 50,000; open orders 3,00,000; new order 4,00,000 → exposure 6,50,000; required 10,50,000 > 10,00,000 → fail `LIMIT_EXCEEDED`, available 3,50,000. With an override of 1,00,000 → pass. Overdue example: oldest due 45 days, max 30 → fail `OVERDUE` even if under the limit. Ticket T-SAL-22.

**BR-SAL-51 When the check runs.** At order `approve` (always); at `dispatch` (when `credit_check_at_dispatch`: only the **hold / overdue / blocked** tests, because the order value is already part of `open_orders`); after every receipt or credit note post for the customer's ACTIVE holds (auto-release when the check passes now); and by the nightly job. A dispatch while the customer has an ACTIVE hold (this order's or a customer-level one) and no valid override → 409 `CREDIT_HOLD`. Ticket T-SAL-22, T-SAL-25.

**BR-SAL-52 Hold and release.** A failed check on approve → order status On Hold (`hold_reason`), `credit_check_passed = false`, a `credit_holds` row ACTIVE (reason code, exposure, limit) and `credit_profiles.hold_status = 'ON_HOLD'`. `release-hold` needs `approve` on `sales-credit`, the releaser ≠ order creator (403 `SELF_APPROVAL_FORBIDDEN`), a reason ≥ 5 characters; optional `overrideUntil` (≤ today + 30 days; default today + 7) and `overrideAmount` (default: the shortfall `required − limit`); the hold becomes RELEASED, the order returns to Approved (reservations proceed), `hold_status = 'OVERRIDE'` while an override is valid, else `NONE`. Auto-release (BR-SAL-51) uses the user who posted the receipt and the reason "Auto: exposure now within limit". `block` / `unblock` of a customer (party status) needs `approve`. Audit `CREDIT_HOLD_CREATED` / `CREDIT_HOLD_RELEASED`. Ticket T-SAL-22.

**BR-SAL-53 Risk grade.** Over the last 12 months of the customer: `avgDaysLate` = Σ(max(0, last_allocation_date − due_date) × invoice_amount) / Σ invoice_amount of fully paid invoices; `latePct` = amount of invoices paid late or still overdue / total invoiced × 100; `bounced` = count of Bounced receipts; `overduePct` = overdue AR / AR × 100. `score = 100 − min(40, 2 × avgDaysLate) − min(30, 0.3 × latePct) − min(20, 10 × bounced) − min(10, 0.1 × overduePct) + (customer_since ≤ today − 2 years ? 5 : 0)`, floored 0, capped 100. Grade A ≥ 80, B ≥ 60, C ≥ 40, D < 40. A customer with no invoices in the window is B. Example: avgDaysLate 10 → −20; latePct 50 → −15; no bounce; overduePct 20 → −2; tenure 3 years +5 → score 68 → B. Stored as `risk_grade_computed`; `accept-grade` copies it to `risk_grade`. Ticket T-SAL-22.

**BR-SAL-54 Credit limit changes.** Editing `parties.credit_limit` needs `edit` on `sales-credit`; **removing a limit (NULL) or raising it by more than 50 % or ₹10,00,000** needs `approve`; every change is audited `CREDIT_LIMIT_CHANGED` with before and after. Lowering below current exposure is allowed and affects new orders only. Ticket T-SAL-22.

### 6.6 Ownership, parties, CRM

**BR-SAL-60 Data scope and cross-department reading.** All document and CRM repositories add, in SQL: the unit filter (context unit, or all units for ADMIN+), soft-delete filter, and the scope predicate: `OWN` → `created_by = me OR owner_user_id = me OR salesperson_id = me`; `DEPARTMENT` → `department = my department` (the column copied from the creator's department at insert); `ALL` → none. A row outside the scope answers **404**. Cross-department reading: users of **Finance** with `view` and scope DEPARTMENT read **all owners** of `sales-orders, sales-invoices, sales-collections, sales-credit, sales-returns, crm-customer360`; **Warehouse** of `sales-orders, sales-reservations, sales-delivery, sales-dispatch, sales-returns`; **Service** of `crm-customer360, crm-feedback, sales-invoices` (a table `CROSS_DEPT_READ` in `apps/api/src/modules/sales/common/scope.ts`). Writes always follow the normal action grants and scope. Ticket T-SAL-06.

**BR-SAL-61 Customer status rules.** Blocked → no new quotation, order, dispatch, invoice (422 `CUSTOMER_BLOCKED`), receipts and credit notes still allowed. Inactive → no new documents (422 `CUSTOMER_INACTIVE`). A `PROSPECT` may get quotations; the first approved order sets `customer_stage` to `NEW`. Invoicing needs GSTIN or `gst_registration_type = UNREGISTERED`. Ticket T-SAL-09.

**BR-SAL-62 Customer creation and duplicates.** GSTIN: 15 characters + checksum (existing validator), PAN = GSTIN characters 3-12 when both given; **duplicate GSTIN** among live parties of the company → 409 `DUPLICATE` (`fields.gstin`); same lower-cased name and state → 409 `DUPLICATE`; same PAN and name trigram similarity ≥ 0.85 → warning (`warnings[]`, not blocking). Lead conversion matches in this order: GSTIN, then `party_contacts` mobile / email, then exact name + city. Ticket T-SAL-09.

**BR-SAL-70 Lead qualification gates.** `qualify` needs: (a) mobile or email; (b) `requirement` ≥ 10 characters; (c) `expected_value > 0` or `expected_close`; (d) an owner; (e) `qualification_score ≥ qualify_min_score` (50). Failure → 422 `QUALIFICATION_GATE`, `fields` = the missing items (`{requirement:"…", score:"Score 38 is below 50"}`). Ticket T-SAL-11.

**BR-SAL-71 Lead scoring (0-100).** Points, summed, capped at 100, then decay: **Budget** (max 20): `expected_value ≥ 10,00,000` → 20; `≥ 1,00,000` → 12; `> 0` → 5. **Authority** (15): `is_decision_maker` → 15; else designation matches `/director|owner|ceo|md|head|manager|purchase|procurement|gm/i` → 8. **Need** (20): requirement length ≥ 50 → 20; ≥ 10 → 10. **Timeline** (15): `expected_close` within 30 days → 15; within 90 days → 8. **Fit** (15): valid GSTIN 5; valid mobile 5; business e-mail (not gmail / yahoo / outlook / hotmail / rediffmail) 5. **Engagement** (15): `min(15, 3 ×` count of timeline entries of type CALL, EMAIL, WHATSAPP, MEETING, FOLLOWUP (done) of this lead in the last 30 days`)`. **Source** (5): the source's conversion rate ≥ `source_conversion_green_pct`. **Decay:** after capping, subtract `10 ×` the number of full 30-day periods since the later of `last_activity_at` and `created_at` beyond the first 30 days; floor 0. Recomputed on every lead change, every timeline entry of the lead, and nightly.
Example: value 15,00,000 (20) + decision maker (15) + requirement 60 chars (20) + close in 20 days (15) + GSTIN, mobile, company e-mail (15) + 2 calls in 30 days (6) + green source (5) = 96. Inactive for 65 days → 2 full periods beyond the first 30? (65 − 30 = 35 → 1 full 30-day period) → −10 → 86. Ticket T-SAL-11.

**BR-SAL-72 Lead conversion.** Only from Qualified (409 `CONFLICT` otherwise; a repeat answers 409 with the existing ids). One transaction: resolve the customer (BR-SAL-62 order). If an existing customer matches and the client did not send `linkPartyId` → 409 `CUSTOMER_EXISTS` with `{partyId, code, name}`. Otherwise create the customer: code `CUS/00001` style (company-wide sequence), name = company else lead name, `legal_name` = company, `party_type` COMPANY (INDIVIDUAL when no company), gstin, state, `customer_stage = 'PROSPECT'`, status ACTIVE, `sales_person_id` = lead owner, a primary contact (lead name, mobile, e-mail, designation), `source_lead_id`. Create the opportunity at stage Qualified (probability 25) named `"<company or lead name> - <first 60 characters of requirement>"`, value, close, owner, priority Medium. Lead → Converted (`converted_party_id`, `converted_opportunity_id`, `converted_at`); links `document_links(LEAD → OPPORTUNITY)`; timeline entries on lead, opportunity and customer; audit `LEAD_CONVERTED`. Ticket T-SAL-11.

**BR-SAL-73 Lead duplicate detection.** Normalised mobile = last 10 digits; e-mail lower-cased; company key = lower-case name with `pvt`, `private`, `ltd`, `limited`, `llp`, `inc`, punctuation and spaces removed. Same mobile or e-mail as a live non-disqualified lead → 409 `DUPLICATE` with `matches:[{id, code, name, reason, score}]` (also enforced by the partial unique indexes). Company key similarity (pg_trgm `similarity`) ≥ 0.95 → 409 `DUPLICATE`; ≥ 0.85 → success with `warnings:[{code:'SIMILAR_LEAD', matches}]`. `overrideDuplicate: true` plus `approve` permission bypasses the 0.95 block (not the unique index). Existing customers with the same GSTIN / mobile are reported as `existingCustomer` (non-blocking). Ticket T-SAL-11.

**BR-SAL-74 Opportunity stage gates and moves.** `move-stage {stage, reason?, lossReasonId?}` (with `If-Match`): rejects Won / Lost records (409 `OPPORTUNITY_LOCKED`; `reopen` needs `approve`). **Forward skip** (target sort − current sort > 1) is allowed only when `allow_stage_skip` or the user has `approve` (422 `STAGE_SKIP`), always allowed to Lost. **Backward** moves need `reason ≥ 5` characters. **Gates (entering a stage):** every column in `required_fields` of the target stage must be set (`expected_value > 0`, `primary_contact`, `expected_close`); **Negotiation** needs ≥ 1 linked quotation in Sent, Approved or Accepted; **Won** needs a linked quotation Accepted or a linked non-cancelled sales order; **Lost** needs `lossReasonId`. Failure → 422 `STAGE_GATE_FAILED` with `fields`. Success: new stage, `stage_entered_at`, `probability_pct` = stage default (and `probability_manual = false`), `forecast_category` (BR-SAL-81), status (Won / Lost / Open), `closed_at` for Won / Lost, a `opportunity_stage_history` row (`days_in_from_stage`), a timeline entry; Won sets a PROSPECT customer to NEW. System moves: first quotation Sent while stage = Proposal → Negotiation; an order Approved that is linked to the opportunity → Won. Example: move to Won with only a Draft quotation → 422 `STAGE_GATE_FAILED` ("Won needs an accepted quotation or a sales order"). Ticket T-SAL-12.

**BR-SAL-75 Create quotation from an opportunity.** Allowed for Open deals at stage Qualified or later; creates a Draft quotation (customer, salesperson, opportunity, valid_till default, the customer's price list) with no lines; links `document_links(OPPORTUNITY → QUOTATION)`; a Draft quotation already linked to the opportunity → 409 `DRAFT_EXISTS` with its id (double-click protection). Ticket T-SAL-19.

**BR-SAL-76 Stale and overdue deals.** `lastActivity = max(last_activity_at, stage_entered_at, updated_at)`; stale when `now − lastActivity > stale_days` (default 14); overdue when `expected_close < today` and Open. Shown as a red dot on the card and in the Exceptions tab. Ticket T-SAL-12.

**BR-SAL-80 Lead and win KPIs.** Lead conversion % (cohort) = converted leads ÷ leads created in the period × 100; win rate = Won ÷ (Won + Lost) by count (and by value) of opportunities closed in the period; average cycle days = average of `closed_at::date − doc_date` of Won; pipeline value = Σ `expected_value` of Open deals; weighted pipeline = Σ `expected_value × probability_pct / 100` of Open (On Hold excluded). Example: 40 leads created, 6 converted → 15.0 %; 12 won + 8 lost → 60.0 %. Ticket T-SAL-17.

**BR-SAL-81 Probability and forecast category.** Stage defaults 10 / 25 / 50 / 75 / 100 / 0. A manual probability (allowed on Open, 0-99) sets `probability_manual`; the next stage move resets to the stage default. Forecast category: Won → Closed; Lost → Omitted; probability ≥ 75 → Commit; ≥ 50 → Best Case; else Pipeline. Monthly forecast = Σ weighted values by `expected_close` month. Example: ₹10,00,000 at 50 % → weighted ₹5,00,000, Best Case. Ticket T-SAL-12.

**BR-SAL-82 Follow-ups.** Create: due date ≥ today (422 `DATE_IN_PAST`), subject exists and is in scope. `done` needs `outcome`; `completed_at = now`; if `nextFollowUp > today` a new Planned follow-up is created (same subject, related record, channel, owner, purpose "Follow-up of <code>") and linked in the timeline. The mirrors `leads.next_follow_up` and the customer's next action (purpose and due date of the earliest Planned follow-up) are recomputed after every follow-up change. Overdue = Planned and (`due_date < today`, or due today and `due_time < now`). The nightly job marks Planned follow-ups with `due_date < today − 1` as Missed, sends reminders (`reminder_sent_at`) `followup_reminder_hours` before the due time (timeline `REMINDER`) and escalates (sets `escalated_at`, timeline entry for the owner's manager) after `followup_escalate_days` overdue days. On-time completion % = Done with `completed_at ≤ end of due_date` ÷ (Done + Missed) × 100. Ticket T-SAL-13, T-SAL-33.

**BR-SAL-83 Source cost and ROI.** `months = max(1, months elapsed from FY start to today)`; `cost = monthly_cost × months`; `costPerLead = cost / leads`, `costPerQualified = cost / qualified`, `costPerWon = cost / won` (null when the divisor is 0); `revenue` = Σ `taxable_total` of Posted invoices dated in the FY for customers whose `source_lead_id` has this source; `ROI % = (revenue − cost) / cost × 100` (null when cost = 0). Example: monthly cost 20,000 for 7 months = 1,40,000; revenue 8,40,000 → ROI 500.00 %. Ticket T-SAL-17.

**BR-SAL-84 DSO.** `DSO = AR outstanding now ÷ credit sales of the last 90 days × 90` (credit sales = Σ `grand_total` of Posted invoices dated in the last 90 days; AR = Σ balances). Example: AR 24,00,000; last-90-day sales 60,00,000 → 36.0 days. Per customer and per unit the same formula. Ticket T-SAL-32.

**BR-SAL-85 Consent (DPDP Act 2023).** `record-consent {purpose (required), channel (WhatsApp, SMS, Email, Phone, All), proofRef?}` sets Granted, `consent_at`, purpose; `withdraw-consent` sets Withdrawn immediately (always allowed); a Granted consent older than `consent_valid_months` (24) becomes Expired in the nightly job. `ConsentService.canMarket(subject, channel)` → `{allowed, reason}`: allowed only when Granted, not expired and the channel is covered; **marketing / promotional messages are blocked otherwise**; transactional messages (quotation, order confirmation, delivery, invoice, payment reminders for an existing contractual relationship) are not marketing and are allowed. Every consent change is audited (`CONSENT_CHANGED`) and written to the timeline. The Communication module must call `canMarket` before any marketing send. The DPDP Rules were notified in November 2025; most obligations apply 18 months later (consent-manager provisions earlier) — the design collects purpose, time and proof now so the data is ready (timing from the sources in §15). Ticket T-SAL-08.

**BR-SAL-86 Customer stage and tier (nightly).** Unless `customer_stage_manual`: PROSPECT stays until the first Approved order (→ NEW); with a Posted invoice dated within 90 days → ACTIVE; last invoice 91-180 days ago → AT_RISK; more than 180 days or none for a customer created over 12 months ago → DORMANT; LOST is manual only. **Tier** by trailing 12-month taxable revenue: sort customers by revenue descending; a customer is A when the cumulative revenue share **before** adding it is < 70 %, B when < 90 %, else C. Example: revenue 100 total: C1 50 (before 0 %) → A; C2 25 (before 50 %) → A; C3 15 (before 75 %) → B; C4 10 (before 90 %) → C. Ticket T-SAL-33.

**BR-SAL-87 NPS, CSAT and detractor follow-up.** Promoters 9-10, passives 7-8, detractors 0-6. `NPS = round1(%promoters − %detractors)` over feedback with an NPS score in the period (range −100..100); CSAT = average `rating`. Example: 10 answers, 5 promoters, 3 passives, 2 detractors → 50 − 20 = 30.0. A saved feedback with NPS ≤ 6 or rating ≤ 40 creates a Planned follow-up for the owner (priority High, due the next working day, Sunday skipped, purpose "Detractor feedback <code>", `source_feedback_id`). `close` needs a Corrective Action and sets the closure date (≥ feedback date). Ticket T-SAL-14.

**BR-SAL-88 Quotation conversion %.** Cohort by `sent_at` in the period: `converted = Σ sent quotations that have a linked order`; `% = converted ÷ sent × 100` by count and by value (`grand_total`). Ticket T-SAL-32.

**BR-SAL-89 OTIF.** For each dispatched order line with a promise date `p = line.delivery_date ?? order.promise_date`: `delivery date = dispatch.pod_date ?? dispatch.doc_date`; **on time** when the delivery date ≤ `p`; **in full** when the quantity delivered on or before `p` ≥ `qty − cancelled_qty`. `OTIF % = lines that are on time and in full ÷ lines whose promise date falls in the period × 100`. Plan `otif_status`: Pending until all lines are delivered or the promise date has passed; then Late (delivered after p, in full), Short (on time, not in full), Late and Short, or On Time In Full. Example: promise 10 Nov, 100 nos: dispatch 9 Nov 100 → On Time In Full; 12 Nov 100 → Late; 9 Nov 80 and nothing more after 10 Nov → Short; 12 Nov 80 → Late and Short. Ticket T-SAL-24 (status), T-SAL-32 (KPI).

**BR-SAL-90 Receivable ageing.** Buckets of `balance` by days past due: Current (not yet due), 1-30, 31-60, 61-90, over 90 (`v_sales_receivable.bucket`). The customer statement lists `v_customer_ledger` rows ordered by `doc_date, created_at` with a running balance `Σ debit − Σ credit`. Ticket T-SAL-32.

### 6.7 Cross-cutting

**BR-SAL-91 Concurrency, idempotency, lock order, double click.** Every action that changes money or stock takes an `Idempotency-Key` (existing helper), runs in **one transaction** and re-reads the status **inside** the transaction after taking the lock. Lock order (always ascending, never reversed): customer `credit_profiles` row → order → order lines (by `line_no`) → dispatch → stock balances (by `item_id`, then `warehouse_id`) → invoices (by `id`) → collection → allocations. Optimistic locking `version` / `If-Match` on every PATCH and action that edits fields (409 `VERSION_CONFLICT`). A second post / dispatch / approve of the same record gives 409 `CONFLICT` (or the replay response with the same key). Ticket: every service ticket; proven in T-SAL-36.

**BR-SAL-92 Financial year and dates.** Create and every posting action need the document's FY to be OPEN (409 `PERIOD_CLOSED`); document dates (quote, order, invoice, dispatch, receipt, return, feedback) may not be in the future (422 `DATE_IN_FUTURE`) and must lie in the FY (422 on the field); planning dates (promise, valid till, expected close, due, planned) may. Ticket T-SAL-06.

## 7. API design

### 7.0 Common rules
* Base `/api/v1`. Routers (mounted in `app.ts` **before** the pages router, after plan 03's): `createSalesPagesRouter()` (`/pages`: panels and sub-resources of the 18 pages), `createSalesRouter()` (`/sales`), `createCrmRouter()` (`/crm`), `createSalesLookupsRouter()` (`/lookups`). Each applies `authenticate, requirePasswordChanged, resolveContext`; every write needs `requireConcreteUnit` and `requirePageAction(pageId, action)`; `Idempotency-Key` on every POST that changes data; `If-Match: <version>` on PATCH and on actions that edit fields. Success `{data, meta?}`; error `{error:{code,message,status,requestId,fields?}}`.
* **Typed page endpoints** are the existing ones (`GET /pages/:pageId/schema`, `GET|POST /pages/:pageId/records`, `GET|PATCH|DELETE /pages/:pageId/records/:id`, `POST …/restore`, `POST …/records/:id/actions/:action`, `GET …/export.xlsx`, `GET …/audit`); the row shape, `data` keys, filters, totals and statuses of the 18 pages are in `04a`. List filters are query parameters named by the schema `filters[].param` (e.g. `?status=Qualified&owner=<uuid>&scoreMin=50&dueFrom=2026-11-01`).
* `schema` additions per page (from `04a`): `tabs` (the 6 frozen labels), `tabPanels:[{tab,key,scope}]` (7.9), `registerTab?` not needed (the existing rule gives the register tab), `kind:'typed'`, `master` true for `crm-sources`, `sales-pricelist`, `sales-credit`, `crm-customer360`.
* **Action contract**: `POST /pages/:pageId/records/:id/actions/:action` body = JSON object (validated per action with zod, unknown keys 422); response `{data: TypedRecordDto, meta:{replay?:true}}`; wrong status → 409 `CONFLICT`; missing permission → 403 `FORBIDDEN` (after the 404 of a hidden row). `SchemaAction.requires` ∈ `add | edit | delete | approve` (plan 03 widened it); `requiresFrom` as in Inventory.
* Documents with lines: `data.lines` on `GET …/records/:id`, `POST …/records` and `PATCH …/records/:id` (plan 03 C4, whole array replaces, `lineNo` assigned by the server).
* Line JSON (zod names in `apps/api/src/modules/sales/schemas/lines.ts`): **`SalesLineInput`** `{ itemId?: uuid, description: string(1..300), hsnSac?: string, qty: number>0 (3 dp), uom: string, rate?: number>=0 (6 dp; omitted = the price engine fills it), discountPct?: number 0..100, discountAmount?: number>=0 (never both), taxCodeId?: uuid, warehouseId?: uuid, deliveryDate?: date, customerPartNo?: string }`; on read each line adds `lineNo, listRate, priceSource, costRate, marginPct, grossAmount, discountAmount, chargesShare, taxableValue, cgstRate…cessAmount, lineTotal, reservedQty, deliveredQty, invoicedQty, returnedQty, cancelledQty` (orders) or `invoicedQty` (dispatch lines). Dispatch lines `{orderLineId, qty, batchNo?, serialNos?: string[]}`; plan lines `{orderLineId, plannedQty}`; invoice lines are created from the source only (`data.lines` PATCH on a Draft invoice may change `qty` downward and `description`); return lines `{invoiceLineId, qty, reasonCode?, conditionNote?, disposition?}`; credit-note lines `{invoiceLineId, qty? , amount?}`.
